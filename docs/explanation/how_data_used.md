# How data are used for model training?

## `features.py` — The Feature Engineering Hub

This file is the **shared foundation** that every other pipeline script imports. It does three things:
1. **Load** all raw tables into memory
2. **Build** the master feature panel
3. **Shape** that panel into training/inference data for the models

Think of it as the "assembly line" that transforms raw sales data into ML-ready inputs.

---

## Section 1: Data Loading

### `_load_tables_parquet()` — Parquet Fallback Loader
```python
# Loads 8 tables from data/processed/*.parquet
["demand_history", "sku_master", "locations", "lanes",
 "distributors", "promo_calendar", "flu_index", "inventory_batches"]
```
This is the **offline/demo fallback**. If MySQL is down, it reads the `.parquet` files generated by `build_dataset.py`.

---

### `load_tables()` — Primary Data Source with Fallback

```
MySQL pharma_sc  ──→  db/inputs.py  ──→  returns dict of DataFrames
      ↓ (on failure)
data/processed/*.parquet
```

- Tries MySQL **first** (production mode)
- On **any** exception (network, auth, missing tables), silently falls back to parquet
- Returns the exact same dictionary shape either way — so all callers are oblivious to the data source

**Why this pattern?** It allows the same codebase to run in both production (MySQL-backed) and demo mode (parquet-backed) without any code changes.

## Section 2: `build_promo_grid(dates)` — Promo Coverage Table

### What it generates:

| date | region | promo_uplift |
|---|---|---|
| 2018-12-15 | WH_NAGPUR | 0.25 |
| 2018-12-15 | WH_LUCKNOW | 0.25 |
| 2018-10-05 | ALL regions | 0.15 |

### How it works:
- Reads `promo_calendar.parquet` (4 campaigns from config)
- For each promo, expands it into **one row per (date, region)** within the promo's date range
- If multiple promos overlap on the same date+region, takes the **max uplift** (not additive)

### Why it generates this:
The model needs to know on any future forecast date "is there a promo running here?". This grid is the lookup table that answers that. It's used:
1. In `build_panel()` for training (what was the promo uplift on historical training days?)
2. In `build_covariates()` for inference (what will the promo uplift be on future forecast dates?)

## Section 3: `build_panel(tables)` — The Master Feature Table

**This is the most important function.** It creates the single wide DataFrame that everything trains and predicts from.

### What it joins together:

```
demand_history  (date, sku_id, atc_code, region, units)
       +
sku_master      (sku_id → criticality, unit_cost_inr)
       +
locations       (location_id → type, demand_share)
       +
flu_index       (date, region → flu_index)
       +
promo_grid      (date, region → promo_uplift)
       =
panel           (one row per day × sku × region, with ALL features)
```

### Lag features generated:

| Column | What it is | Why it's needed |
|---|---|---|
| `lag_1` | units sold 1 day ago | Captures yesterday's momentum |
| `lag_7` | units sold 7 days ago | Same weekday last week (strong weekly seasonality in pharma) |
| `lag_14` | units sold 14 days ago | Two weeks ago |
| `lag_28` | units sold 28 days ago | Same day ~4 weeks ago (monthly cycle) |
| `lag_364` | units sold 364 days ago | Same weekday last year (annual seasonality); filled with `roll_mean_28` if missing |

**Why lags at these specific intervals?** Pharmacy demand has strong weekly periodicity (prescriptions follow doctor visit patterns) and annual seasonality (flu, monsoon, festivals). Lag 364 captures "what was demand doing this same week last year?"

### Rolling statistics generated:

| Column | What it is | Why it's needed |
|---|---|---|
| `roll_mean_7` | 7-day rolling mean of units (lagged by 1) | Short-term trend level |
| `roll_std_7` | 7-day rolling std dev (lagged by 1) | Short-term demand volatility |
| `roll_mean_28` | 28-day rolling mean (lagged by 1) | Medium-term baseline level |

> **Important:** All rolling stats use `.shift(1)` before rolling. This means "the 7-day mean of the 7 days *before* today" — prevents **data leakage** (the model never sees the current day's units when computing the features for that day).

### Calendar features generated:

| Column | Values | Why |
|---|---|---|
| `dow` | 0–6 (Monday=0) | Weekday patterns — Monday prescriptions surge |
| `week_of_year` | 1–52 | Seasonal position in year |
| `month` | 1–12 | Monthly patterns (flu peaks in Jan, monsoon in July) |
| `is_weekend` | 0/1 | Pharmacies have reduced B2B orders on weekends |

### Category/static features generated:

| Column | Values | Why |
|---|---|---|
| `criticality_code` | 0=low, 1=standard, 2=high, 3=critical | Higher criticality → different demand patterns (consistent baseline, less elasticity) |
| `is_tier2` | 0/1 | Tier-2 warehouses have different demand patterns vs. metro DCs |
| `unit_cost_inr` | e.g. 280 | Cost affects ordering behavior; expensive drugs ordered more carefully |
| `demand_share` | 0–1 | Location's share of national demand — size proxy |
| `flu_index` | 2–115 | Current flu severity in region (raw, for model to use contextually) |
| `promo_uplift` | 0.0–0.25 | Active promotional discount/uplift |

## Section 4: `build_covariates(tables, panel)` — Future Covariate Grid

### What it generates:

A `(date, region)` grid that extends into the **future**, covering:
- All historical dates in the panel
- **Plus** any future flu_index readings (epidemiological data arrives before sales data)

```python
# Example output
date        | region      | flu_index | promo_uplift
2019-01-18  | DC_MUMBAI   | 87.3      | 0.0
2019-01-18  | WH_NAGPUR   | 91.1      | 0.25  ← Winter promo active
2019-01-25  | DC_MUMBAI   | 94.2      | 0.0
```

### Why it's needed:
When making a forecast for "42 days from now", the model needs to know:
- Will there be a flu outbreak then? (flu_index for that future date)
- Will there be a promo running then? (promo_uplift for that future date)

These are the **future exogenous covariates** (in ML terminology). `build_covariates()` assembles them so that `melt_horizons()` can join them onto each forecast row.

## Section 5: `make_supervised(panel, stride=7)` — Training Data Shaper

### What it does:

Takes the panel and for each row creates **42 target columns** by shifting the `units` series forward:

```python
target_1  = units shifted -1   # what will demand be tomorrow?
target_2  = units shifted -2   # in 2 days?
...
target_42 = units shifted -42  # in 42 days?
```

### The `stride` parameter:
- Default `stride=7`: only keeps **every 7th day** as a training sample
- This reduces training data size ~7× for backtesting (fast)
- `stride=1` during inference: use every single day's data

### Why 42 targets?
Because `horizon_days = 42` in config. The system forecasts 6 weeks ahead — enough for one full replenishment cycle (lead time ~14 days + review period 7 days + buffer).

### Rows dropped:
```python
work.dropna(subset=["lag_28", "roll_mean_28"])
```
Any row where there isn't enough history to compute a 28-day lag is discarded. This means the first ~28 days of each SKU-region's history are unusable as training samples.

## Section 6: The `FEATURES` List — Exactly What LightGBM Sees

```python
FEATURES = [
    "horizon",          # h=1..42 — the forecast step
    "lag_1",            # yesterday's demand
    "lag_7",            # last week
    "lag_14",           # 2 weeks ago
    "lag_28",           # 4 weeks ago
    "lag_364",          # last year
    "roll_mean_7",      # 7-day moving average
    "roll_std_7",       # 7-day volatility
    "roll_mean_28",     # 28-day moving average
    "futr_dow",         # day-of-week AT the forecast date (not cutoff date)
    "futr_week_of_year",# week number AT the forecast date
    "futr_month",       # month AT the forecast date
    "futr_is_weekend",  # is the forecast date a weekend?
    "futr_promo_uplift",# promo uplift on the forecast date
    "futr_flu_index",   # flu index on the forecast date
    "criticality_code", # drug importance
    "unit_cost_inr",    # drug cost
    "is_tier2",         # location type
    "demand_share",     # location's national share
]
```

> **Critical design note:** Calendar features are prefixed `futr_` — they refer to the **target forecast date**, not the cutoff date. This is intentional: if you're predicting demand for a Monday 3 weeks from now, the model needs to know "that day is a Monday" — not what day of week it is today.

## Section 7: `melt_horizons(supervised, panel, ...)` — Final Training Table Assembly

### What it generates:

Takes the wide `supervised` table (one row, 42 target columns) and **unpivots** it into a long table — one row per `(cutoff_date, sku_id, region, horizon)`:

```
Before (supervised):
date        | sku_id    | region    | lag_1 | target_1 | target_2 | ... | target_42
2018-04-01  | N02BE-01  | DC_MUMBAI | 230   | 245      | 212      | ... | 278

After (melted):
horizon | sku_id    | region    | lag_1 | target | cutoff_date | forecast_date | futr_dow | futr_flu_index
1       | N02BE-01  | DC_MUMBAI | 230   | 245    | 2018-04-01  | 2018-04-02    | 0        | 83.1
2       | N02BE-01  | DC_MUMBAI | 230   | 212    | 2018-04-01  | 2018-04-03    | 1        | 84.2
...
42      | N02BE-01  | DC_MUMBAI | 230   | 278    | 2018-04-01  | 2018-05-13    | 0        | 22.7
```

### Why this structure?
LightGBM is a **tabular** model — it needs one flat row per prediction. By treating `horizon` as a feature column (rather than training 42 separate models), the system:
- **Pools data** across all horizons — rare SKUs benefit from more training samples
- **Shares patterns** — if demand is high on Mondays at horizon 3, it's probably also high at horizon 10
- **Stays consistent** — one model makes all 42-day predictions in one pass

The `require_target=False` mode is used during **inference** — at prediction time, there are no real targets yet (we're forecasting the future), so those rows are included anyway.

## Summary: Data Flow Through `features.py`

```
load_tables()
    ↓ returns 8 DataFrames
    
build_panel(tables)
    ↓ joins all tables
    ↓ adds lags (1,7,14,28,364)
    ↓ adds rolling stats (mean/std 7d, mean 28d)
    ↓ adds calendar features
    ↓ adds category statics
    → panel: (date × sku × region) with ~25 columns

build_covariates(tables, panel)
    ↓ region × date grid extended into future
    → cov: flu_index + promo_uplift for future dates

make_supervised(panel, stride)
    ↓ adds 42 target_{h} columns by shifting
    ↓ drops rows with insufficient history
    → supervised: training-ready rows

melt_horizons(supervised, panel, cov)
    ↓ unpivots 42 targets → long format
    ↓ joins future covariates on forecast_date
    → melted: one row per (cutoff, sku, region, horizon)
              with FEATURES + target column
              → fed directly into LightGBM
```
